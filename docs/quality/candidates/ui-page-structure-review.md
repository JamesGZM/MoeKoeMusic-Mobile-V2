## 原始漏检

个人主页已经通过视觉符合度、截图回归和模块依赖校验，但 `UserProfileScreen.kt` 仍集中 672 行、多组独立视觉区域、页面状态和 11 个回调参数，并绕过已有 `MoeButton` 与 `MoeArtwork`。规则文本已经要求单一文件职责，说明缺口发生在完成流程的触发与验证覆盖，而不是知识缺失。

## 候选复核行为

实质新增或修改 Compose 页面时，在宣布完成前输出一份简短页面结构复核：

1. 列出受影响 UI 文件、行数和每个文件的主要职责。
2. 列出 Screen 的状态输入与事件面；事件参数明显扩张时评估具名事件模型，不以固定数量自动失败。
3. 对照 `docs/UI_COMPONENT_CATALOG.md` 检查直接使用 Material 组件或重复视觉外壳是否绕过已 Adopt/Stable 的公共组件。
4. 先确认当前切片是纯 UI 还是完整业务切片；纯 UI 切片不得为了目录形式虚构 ViewModel、Repository 或 Hilt 接线。
5. 页面专属组合默认保留在 Feature 内；只有存在至少两个真实消费者或必须全局统一的行为约束时，才提议进入 Design System。

## 报告触发信号

以下信号要求给出拆分或保留说明，但候选阶段不直接令构建失败：

- 单个生产 Kotlin 文件通常超过 300 行。
- 同一文件存在两个以上可独立变化的页面区域、状态实现、导航或业务角色。
- Screen 暴露大量同层级回调，新增操作持续扩大函数签名。
- 页面直接实现目录中已处于 Adopt/Stable 状态的组件语义。

行数不是唯一标准。短文件仍可能职责混杂，长文件也可能因强内聚而合理；结论必须结合变化原因、可见性和测试边界。

## 历史回归断言

使用修复前个人主页作为历史样本时，候选必须：

- 要求把页面壳、Hero、概览、歌单和状态实现按 Feature 私有职责拆开。
- 建议将页面操作收敛为明确事件模型。
- 识别错误态按钮与歌单封面的公共组件复用机会。
- 保留首个视觉切片不新增 ViewModel 的既定边界。
- 保留 `EditProfileButton`、`ProfileHero` 等页面专属组合在 `:feature:profile`。

如果只以 `>300` 行为由机械失败，或要求把所有子 Composable 上提 Design System，候选判定为误报；如果强制新增 ViewModel，则违反已批准的切片范围。
